# SP3 viewer adversarial review 2

Reviewed 2026-10-11 against revision 1 of the [specification](../2026-10-11-sp3-viewer-design.md) and [plan](../../plans/2026-10-11-sp3-viewer.md), plus global C6/C7/packaging and decisions D9/D35. Independent document/source review; no production implementation or browser support is claimed. References to SP3 line numbers below refer to revision 1.

**Disposition: revise before approval.** The separation of codec capability from sink capability, actual Safari gate, independent export clock, original-byte HTML embedding, and explicit D9 approval gate are sound. The following contract gaps can invalidate required exports even if the proposed happy-path tests pass.

## Blocking findings

### R2-1 — P1: Streaming output and four submissions do not bound video metadata

**Where:** spec §9, lines 160–168; plan Tasks 1.3 and 8.1–8.3; global C7.5.

Only PNG has a frame-count maximum. A finite interval and positive finite rate allow arbitrarily many video frames, and their arithmetic can overflow or cease to produce distinct safe timestamps. A four-submission queue bounds neither the muxer's metadata nor allocations at finalization. Mediabunny's ordinary MP4 implementation retains a `Sample` per packet in `trackData.samples`, and both ordinary and fragmented paths retain finalized-chunk metadata. This is a confirmed property of the dependency source, not a demonstrated application leak: see [`addSampleToTrack`, `finalizeCurrentChunk`, and `finalizeFragment`](https://github.com/Vanilagy/mediabunny/blob/main/src/isobmff/isobmff-muxer.ts). The source was checked on the review date and must be checked again at the pinned version.

There is also an output-correctness obligation missing from the sink contract: Mediabunny's `StreamTarget` sends positioned writes, including overwrites. A custom OPFS worker adapter that appends each chunk can corrupt MP4 while apparently satisfying “streaming output with backpressure.” The [target documentation](https://mediabunny.dev/guide/writing-media-files#streamtarget) explicitly requires honoring positions and propagating backpressure through media-source submissions.

**Required correction:** specify a finite maximum frame count for every video/PNG path, validate the derived count and integer timestamps before allocating or opening a destination, and budget muxer/index/finalization memory explicitly. A common 100,000-frame cap is a reasonable proposal to measure; it is not established evidence. Choose and pin an MP4 mode, require position-aware ordered sink writes, and bound worker messages as well as encoder inputs. Fragmentation alone must not be advertised as constant memory without inspecting retained indexes. Add long-duration/low-rate rejection, positioned-overwrite, and near-cap sustained-memory tests to Task 1/8; decode and seek the resulting file in external players. A short H.264 feasibility clip cannot establish this guarantee.

### R2-2 — P1: The chosen renderer's default path conflicts with the required CSP

**Where:** spec §3 Scene/UI choice, §§4 and 10–11, especially lines 176 and 188; plan Tasks 1.2, 7.1–7.2.

The plan validates WebGL initialization and single-file bundling separately from the strict production CSP. PixiJS v8's ordinary WebGL path generates JavaScript functions. Its supplied `pixi.js/unsafe-eval` extension, despite the name, replaces those functions with implementations that avoid dynamic evaluation and disables the corresponding renderer checks. This is confirmed in [PixiJS v8.14.3's CSP extension](https://github.com/pixijs/pixijs/blob/v8.14.3/src/unsafe-eval/init.ts) and [shader system](https://github.com/pixijs/pixijs/blob/v8.14.3/src/rendering/renderers/gl/shader/GlShaderSystem.ts). An ordinary bundle can work in development and fail under the promised hash-only offline CSP.

**Required correction:** explicitly select the CSP-safe renderer initialization for both entrypoints before renderer creation, and make Task 1 render a real scene, labels, and the selected batched/particle path under the exact production hash CSP. Ensure the bundler preserves the extension's side effects and produces no runtime import/worker dependency in the offline player. Keep the no-eval policy. Measure performance with this path, since a result obtained using the default generated-function path does not validate the shipped renderer.

### R2-3 — P2: The OPFS cleanup promise cannot span the default changing origin

**Where:** spec §9 line 164 and §11 line 182; plan Tasks 8.3 and 9.1; global C6 loopback trust boundary.

The spec permits retaining staged exports for “next-session cleanup” while defaulting to a fresh port. OPFS belongs to an origin, and the port is part of that origin. A later viewer at another port cannot enumerate or delete the old origin's files. Browser/tab crashes can therefore leave large exports that the next session cannot clean. These are confirmed platform semantics: [OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system) and [origin definition](https://developer.mozilla.org/en-US/docs/Glossary/Origin). As a security consequence inferred from those semantics, a future unrelated loopback service on the old port shares that storage origin; a random OPFS filename is not access control against such a service.

**Required correction:** define staging ownership and retention precisely. Make current-session explicit cleanup available, do not claim cross-port recovery, and document what remains after an interrupted session and how it can be removed. Decide whether residual browser storage is an accepted export/privacy limitation or requires a stronger design; changing the trust boundary silently is insufficient. Do not delete/revoke merely on an anchor click unless the chosen browser path has been shown to retain a usable file snapshot: download initiation is not completion. Test restart on another port, repeated exports, browser interruption, and downloading while cleanup is requested. The latter two are tests to run, not claims that Safari currently fails.

### R2-4 — P2: The advertised PNG limit requires ZIP64, which is absent from the dependency contract

**Where:** spec §9 line 166; plan Tasks 1.5 and 8.4.

A 100,000-frame archive plus its manifest exceeds the traditional ZIP central-directory entry count; high-resolution PNG output can also exceed its 32-bit offsets. Merely selecting a “streaming ZIP” library does not satisfy either requirement. The normative [PKWARE APPNOTE](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT), §§4.4.21–4.4.24, specifies the conventional count/offset field sizes and ZIP64 replacements.

**Required correction:** require streaming ZIP64 support, including central-directory and offset handling, in the feasibility decision; alternatively lower both entry and byte limits to a supported conventional ZIP envelope. Bound the timing manifest as well as ZIP metadata, and enforce limits before finalization can overflow. Test more than 65,535 total entries and a greater-than-4-GiB offset using inexpensive generated/sparse test data where possible, then verify extraction with an independent reader. An archive of a few PNGs does not validate the declared fallback.

## Nonblocking suggestions and implementation gates

### R2-5 — P2 suggestion: Define packaging checks for source, editable installs, and sdist separately

Spec §12 line 192 requires source builds to reject stale assets; Task 1.5 correctly reserves the architecture decision. Specify its result before implementation: asset hashes detect corruption but do not detect a stale build after frontend source changes. A source/build-input fingerprint can cover the workspace and lockfile in a checkout, while an sdist can verify included asset hashes and package compatibility without expecting the excluded `studio/` sources. `pyproject.toml` currently excludes `studio/` from sdists.

Also settle the bootstrap order for editable installs. Both [CI](../../.github/workflows/ci.yml) and [publishing](../../.github/workflows/publish.yml) run `uv sync` before package building, and [CONTRIBUTING](../../CONTRIBUTING.md) starts with that command. A strict Hatch hook applied to editable builds will fail before later frontend build steps unless those workflows are reordered or an explicit development-only policy is defined. Keep release wheels strict; exercise clean-checkout setup, stale frontend input, tampered asset, and offline wheel-from-sdist separately. For the offline build test, pre-provision the declared Python build requirements so a missing Hatchling wheel is not mistaken for a Node dependency.

### R2-6 — P2 suggestion: Flush imperative panels at discrete boundaries and cover structural changes

Spec §8 lines 148–150 sets independent update rates but does not explicitly define the last update on pause, buffering, exact stepping, export completion, and seek completion. Require a synchronous flush of visible time/cursor/KPI/inspector values at those boundaries so a paused exact event cannot show a previous 15 Hz inspector value.

Define ownership for clock-driven structural changes, such as a selected entity retiring or a paged state field appearing. Generic replay really deletes retired entities ([`deltas.ts`](../../studio/packages/trace/src/deltas.ts), lines 45–48). Numeric text refs alone cannot update the live/retired state of a panel. An imperative bounded row adapter or an explicit discrete lifecycle notification can work; do not introduce one React commit per simulation event. Test creation/retirement and field/queue changes during playback, then immediate pause, with React-commit instrumentation.

### R2-7 — P2 suggestion: Make the bootstrap an executable lifecycle, not an unspecified redirect

The per-instance custom-header secret is appropriate for cookie leakage across ports. Spec §11 line 186 should distinguish a bootstrap HTML response from an HTTP redirect: a 3xx response body is not a place to rely on executing the sessionStorage transfer. Define a nonce-protected 200 bootstrap, successful storage transfer, then `location.replace` to the token-free app (or an equivalently explicit protocol); set `Cache-Control: no-store` for credential-bearing responses. Keep an actionable terminal renewal path if browser launch or storage transfer fails after consuming the token, and specify how the terminal issues another link while serving. These are additions to the already-required reused-token and failed-launch tests, not a proposal to weaken authentication.

### R2-8 — P3 suggestion: Freeze frame duration and terminal-frame semantics

Spec §9 line 160 fixes simulation sample times but not encoded frame durations. With start 0, end 1, rate 1, and 30 fps, the described sequence has 30 pre-end frames plus the exact-end frame. If every frame lasts 1/30 s, the file lasts 31/30 s; a fractional interval and a zero-length interval need equally explicit rules. State the intended terminal hold/duration, timestamp rounding, and PNG manifest representation, then use the same schedule oracle in independent video decoding tests. This is a definition gap, not evidence that an implementation currently exports the wrong duration.

## Review limits and acceptance

No application export implementation exists to reproduce browser failures against. Dependency/platform properties above were verified in primary documentation or source on 2026-10-11; actual Safari codec, sink, download, CSP, and memory measurements remain required by the plan. A successful Playwright WebKit run must not close D35. No weakening of D9, C7.2, no-Node sdist packaging, or the read-only SP3 scope is recommended.
